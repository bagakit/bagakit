# 工程证据路线

当意图判定结果是“技术方案、性能验证、根因修复、兼容性 Patch、基础设施落地或部署运行手册”时，加载本路线作为 `protocol` 或 `infrastructure` profile 的增强参考。

本路线服务三个结果：读者能复述结论，执行者能完成下一步，评审者能追溯证据。它增强技术写作交付，不改变 `article.md`、`execution_appendix.md` 和 `review_report.md` 的职责边界。

## 进入条件

至少满足以下一项：

- 文档要推动一个工程决策或落地动作。
- 结论依赖运行数据、日志、代码路径、协议字段或实验对照。
- 读者需要复制配置、执行命令、验证结果或准备回滚。
- 方案可能影响生产环境、凭据、网络边界或数据安全。

不满足这些条件时，继续使用通用文章、研究综合或 `distill` 路线，不套用本路线的执行要求。

## 写前判定

先在 `outline.md` 或 `review_report.md` 写清：

- 读者要做什么决定或动作。
- 结论由哪一类证据支撑：实验、代码追踪、日志、配置、事故记录或用户反馈。
- 验证对象、样本口径、时间窗口和环境边界。
- 不适用场景、已知缺口和失败后的降级路径。

## 正文增强项

按任务类型选择，不要求每篇都完整出现：

1. 先给结论和影响；有实测收益时给出真实测量值。
2. 把根因追到可定位的机制、字段、状态转移、代码路径或配置项。
3. 描述方案如何工作，以及为什么排除至少一个相邻方案。
4. 把可复制的命令、配置、代码和检查步骤放入执行附录。
5. 单独说明安全门禁、权限边界、生产限制和凭据处理。
6. 写出无收益、负收益、不适用条件和回滚或降级动作。

## 验证协议按指标选择

不要把固定样本量或固定分位数当成所有文档的硬门禁：

- 延迟、耗时、资源消耗：记录样本量、环境、对照组和合适的分位数。
- 兼容性、协议和故障修复：记录复现条件、状态变化、日志或字段证据，以及修复后的验收信号。
- 部署和运行手册：记录前置条件、验证命令、成功信号、失败处理和回滚触发器。
- 架构或方案决策：记录候选方案、评价标准、取舍、反例和换挡条件。

任何数字都必须标注来源和验证范围。无法验证的内容写成“待验证”或“来源声称”，不能从配置、默认值或目标指标反推实测结果。

## 交付检查

将路线结果分散到已有交付物：

- `article.md`：结论、机制、取舍和读者需要理解的边界。
- `execution_appendix.md`：命令、配置、环境、验证、恢复和安全门禁。
- `review_report.md`：证据来源、样本边界、未覆盖场景、残余风险和验证状态。

本路线是条件分支。它不替代 Core 的结构、证据、受众和去 AI 味检查，也不要求研究综述、通知、概念解释或单句润色采用执行型结构。
